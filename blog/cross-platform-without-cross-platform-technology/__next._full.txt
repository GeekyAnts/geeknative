You can build natively, with each platform's own language and UI toolkit, and pay for it three times. Or you can share code with a cross-platform framework, and accept a layer between your app and the platform.</p>
<p>For a long time, the second option won on cost. Writing an app once is cheaper than writing it three times. That was the whole argument, and it was a good one.</p>
<h2 id="what-coding-agents-change">What coding agents change<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-coding-agents-change">#</a></h2>
<p>Coding agents are very good at writing an implementation from a clear description. Given a spec, an agent can write a SwiftUI screen, then a Compose screen, then a React page, each in the idioms of its platform. The second and third implementations are no longer the expensive part.</p>
<p>What stays hard is consistency. Three implementations drift. A label changes on one platform. A rule is handled differently on another. A color is a shade off on the web. Without structure, an agent makes this worse, not better, because it can produce three slightly different apps very quickly.</p>
<p>So the problem moves. It is no longer "how do we avoid writing the app three times?" It is "how do we keep three native apps the same product?"</p>
<h2 id="share-everything-except-the-code">Share everything except the code<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#share-everything-except-the-code">#</a></h2>
<p>geeknative's answer is to share everything that defines the product, and nothing that runs it.</p>
<ul>
<li><strong>The product and the behavior.</strong> PRODUCT.md says what the app is and for whom. DESIGN.md says how it looks and what adapts per platform. Each feature has a spec in <code>spec/features/</code> with numbered acceptance criteria.</li>
<li><strong>The brand and the copy.</strong> App identity, design tokens, strings and icons live in <code>contracts/</code>. <code>make gen</code> compiles them into Swift, Kotlin, Android resources, TypeScript and a Tailwind theme. A color or a string has one source, so it can't drift.</li>
<li><strong>The structure.</strong> A feature called <code>notes</code> is <code>NotesScreen</code>, <code>NotesViewModel</code> and <code>NotesRepository</code> on every platform.</li>
<li><strong>The tests.</strong> Each platform's tests carry the acceptance criteria IDs. <code>make parity</code> shows which criteria each platform covers.</li>
</ul>
<p>The code itself is plain SwiftUI, Jetpack Compose and React. No runtime, no bridge, no shared UI kit.</p>
<h2 id="one-loop-for-every-request">One loop for every request<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#one-loop-for-every-request">#</a></h2>
<p>The last piece is the agent's behavior. AGENTS.md teaches any agent the same loop: work out what kind of request it is, update the source of truth first, build the change natively on each platform, verify with <code>make check</code>, record each platform's status and report.</p>
<p>You talk to your agent the way you always do: "add a notes list", "make it feel warmer", "the app crashes when I rotate". The loop keeps every answer consistent across three apps.</p>
<h2 id="when-this-is-the-right-trade-off">When this is the right trade-off<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#when-this-is-the-right-trade-off">#</a></h2>
<p>This isn't the right choice for everyone. Teams with a healthy React Native or Flutter app, a strong JavaScript or Dart team, or a need for desktop apps have good reasons to stay where they are. We wrote honest comparisons with <a href="/geeknative/compare/react-native/">React Native</a>, <a href="/geeknative/compare/flutter/">Flutter</a>, <a href="/geeknative/compare/capacitor-ionic/">Capacitor and Ionic</a> and <a href="/geeknative/compare/kotlin-multiplatform/">Kotlin Multiplatform</a>.</p>
<p>It is a strong choice when native quality matters, when you need new platform features as soon as they ship, and when your team already builds with coding agents. See the <a href="/geeknative/use-cases/">use cases</a> for examples.</p>
