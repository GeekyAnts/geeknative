A feature ships on iOS first and reaches Android a quarter later. Copy differs between stores. The brand refresh lands on one platform and not the other. Every change becomes three tickets in three backlogs.</p>
<p>geeknative gives a coding agent the structure to build every change once in the spec and then natively on each platform, and it shows you where the platforms differ.</p>
<h2 id="what-changes-for-the-team">What changes for the team<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-changes-for-the-team">#</a></h2>
<ul>
<li><strong>One backlog, not three.</strong> A change starts in the spec. The agent builds it on iOS, Android and the web in the same turn, in parallel where the agent supports sub-agents.</li>
<li><strong>Brand and copy can't drift.</strong> App identity, design tokens, strings and icons live in <code>contracts/</code>. <code>make gen</code> compiles them into Swift, Kotlin, Android resources, TypeScript and Tailwind theme code. A color or a string has one source.</li>
<li><strong>Parity is a table, not a hope.</strong> Acceptance criteria are numbered, like <code>AC-notes-1</code>. Each app's tests carry those IDs in their names, and <code>make parity</code> reports which criteria each platform covers.</li>
<li><strong>Engineers can move between apps.</strong> A feature called <code>notes</code> is <code>NotesScreen</code>, <code>NotesViewModel</code> and <code>NotesRepository</code> on every platform, written in each platform's own idioms.</li>
</ul>
<h2 id="a-governed-way-to-use-coding-agents">A governed way to use coding agents<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#a-governed-way-to-use-coding-agents">#</a></h2>
<p>Many engineering leaders are asked to show what coding agents do for productivity. The hard part is not getting code written. It is keeping that code consistent, reviewed and tested.</p>
<p>geeknative is a working pattern for that. AGENTS.md teaches every agent the same loop:</p>
<ol>
<li>Work out what kind of request it is: product, feature, design, copy, bug, platform-specific, engineering or a question.</li>
<li>Update the source of truth first: the spec, PRODUCT.md, DESIGN.md or a contract.</li>
<li>Build the change natively on each platform.</li>
<li>Verify with <code>make check</code>.</li>
<li>Record each platform's status in the spec and report one line per platform.</li>
</ol>
<p>Reviewers read the spec change and the per-platform diffs. Nothing is hidden in a runtime. See <a href="/geeknative/docs/guides/working-with-your-agent/">Working with your agent</a>.</p>
<h2 id="start-with-one-feature">Start with one feature<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#start-with-one-feature">#</a></h2>
<p>You don't need to move a whole product at once. A practical pilot:</p>
<ol>
<li>Create a geeknative project for a new feature area or a small companion app.</li>
<li>Copy your design tokens and key strings into <code>contracts/</code>, and run <code>make gen</code>.</li>
<li>Write the feature's spec with numbered acceptance criteria.</li>
<li>Ask your agent to build it, then compare the three results and the parity report.</li>
</ol>
<p>The <a href="/geeknative/docs/concepts/specs-and-parity/">specs and parity</a> page shows the spec format and the report.</p>
<h2 id="what-to-know-first">What to know first<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-to-know-first">#</a></h2>
<ul>
<li>geeknative creates new projects. It does not convert an existing codebase. To bring an existing app across, use it as the reference for the spec. See <a href="/geeknative/use-cases/add-a-platform/">Add the missing platform</a>.</li>
<li>iOS and Android UI tests are on the <a href="/geeknative/docs/project/roadmap/">roadmap</a>. Today, parity is measured with unit tests on iOS and Android and with rendering tests on the web.</li>
<li>There is no backend layer yet. Features call repository interfaces that you implement against your own APIs.</li>
</ul>
<h2 id="questions-teams-ask">Questions teams ask<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#questions-teams-ask">#</a></h2>
<h3 id="can-platforms-differ-on-purpose">Can platforms differ on purpose?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#can-platforms-differ-on-purpose">#</a></h3>
<p>Yes. A spec has a Platform notes section for intentional differences, and a platform's status can be <code>n/a</code>. The Claude Code stop hook asks once when a turn changed some apps but not others, so a difference is a decision, not an accident.</p>
<h3 id="do-we-have-to-use-claude-code">Do we have to use Claude Code?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#do-we-have-to-use-claude-code">#</a></h3>
<p>No. Any agent that reads AGENTS.md works, including Codex, Cursor, Gemini CLI and GitHub Copilot's coding agent. Claude Code gets extra integration: platform subagents and hooks. See <a href="/geeknative/docs/guides/other-agents/">Other agents</a>.</p>b:X
