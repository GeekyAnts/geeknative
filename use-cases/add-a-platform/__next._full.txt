An iOS app with Android users asking for a version. A web product with "mobile app coming soon" on the pricing page. Adding a platform usually means hiring a new team, or rewriting everything in a cross-platform framework.</p>
<p>With geeknative, the app you already have becomes the reference. The agent writes the spec from it, then builds native iOS, Android and web apps against that spec.</p>
<h2 id="how-it-works">How it works<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#how-it-works">#</a></h2>
<p>geeknative starts new projects. It does not import your existing code. What it imports is your product: what it does, how it looks and how it behaves.</p>
<ol>
<li>
<p><strong>Create a project</strong> with your app's name and ID:</p>
<pre class="shiki geeknative" style="background-color:#f5f4f2;color:#0b0b0b" tabindex="0" data-language="shell"><code><span class="line"><span style="color:#0B0B0B;font-weight:bold">npm</span><span style="color:#0B0B0B"> create</span><span style="color:#0B0B0B"> geeknative@latest</span><span style="color:#0B0B0B"> my-app</span><span style="color:#686664"> --</span><span style="color:#686664"> --name</span><span style="color:#9F0310"> "My App"</span><span style="color:#686664"> --id</span><span style="color:#0B0B0B"> com.acme.myapp</span></span></code></pre>
</li>
<li>
<p><strong>Describe the existing product.</strong> Ask your agent to fill in PRODUCT.md and <code>spec/navigation.md</code> from your current app. Share screenshots, your current copy and, if you have them, existing requirements or test plans.</p>
</li>
<li>
<p><strong>Bring the brand across.</strong> Put your colors, type, spacing and radii in <code>contracts/tokens.json</code>, and your copy in <code>contracts/strings/</code>. <code>make gen</code> turns them into code for every app. See <a href="/geeknative/docs/reference/contracts/">Contracts</a>.</p>
</li>
<li>
<p><strong>Spec one feature at a time.</strong> Each spec in <code>spec/features/</code> gets numbered acceptance criteria. Write them from how your current app behaves today.</p>
</li>
<li>
<p><strong>Build in vertical slices.</strong> The agent takes each feature through all three apps before starting the next. Your existing platform's app is the benchmark for every review.</p>
</li>
</ol>
<h2 id="why-not-only-build-the-missing-app">Why not only build the missing app?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-not-only-build-the-missing-app">#</a></h2>
<p>You can set a platform's status to <code>n/a</code> in a spec and build only what you need. Building all three from the spec has advantages, though:</p>
<ul>
<li>The new app and the replacement for your current one are built the same way, with the same names.</li>
<li>You get parity tracking across every platform, so the next feature reaches everyone at once.</li>
<li>Your current app's technical debt doesn't move into the new platform.</li>
</ul>
<p>Many teams start by building only the missing platform, then move the original app onto the same spec when it needs a major update.</p>
<h2 id="what-to-know-first">What to know first<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-to-know-first">#</a></h2>
<ul>
<li><strong>Your backend stays yours.</strong> geeknative has no backend layer yet. Features use repository interfaces, and you implement them against your existing APIs.</li>
<li><strong>Check minimum versions.</strong> iOS 17, Android 7.0 (API 24), Safari 16.4, Chrome 111 and Firefox 128. Compare them with your analytics.</li>
<li><strong>Plan for review.</strong> The agent writes the code, but someone on your team should know each platform well enough to review it.</li>
</ul>
